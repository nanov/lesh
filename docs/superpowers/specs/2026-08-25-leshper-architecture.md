# leshper — Architecture Decisions

**Date:** 2026-08-25
**Status:** Approved — records the decisions of [map #82](https://github.com/nanov/lesh/issues/82)'s first session
**Companion to:** [`2026-08-25-leshper-requirements.md`](2026-08-25-leshper-requirements.md) (what leshper must do) — this document records *how*, as decided. Each decision's full reasoning lives on its ticket; this is the index a session loads once.

## 1. Vocabulary

Decided in [#84](https://github.com/nanov/lesh/issues/84), recorded in `CONTEXT.md`, binding everywhere: the editor is **leshper**; the editing unit is an **action** (`widget` is reserved for future UI surfaces); an **effect** is what a turn of the state machine emits, never a reactor's output; the lexer+parser are **the syntax layer**; the interactive side is **the UI**; "front end" is retired in every sense.

## 2. The spine and the scoreboard

ADR-0001 reaffirmed ([#85](https://github.com/nanov/lesh/issues/85)): POSIX sh is the spine, the flavour is lesh's own, deviations lean zsh, admitted one at a time with divergences counted. The yash suite stays the scoreboard, dash the differential authority. Nothing leshper does may move either without a recorded decision.

## 3. The syntax layer is leshper's public API

**C-1 through C-6 are frozen** as of [#103](https://github.com/nanov/lesh/issues/103)/[#104](https://github.com/nanov/lesh/issues/104): the parser is total, spans are real input offsets, `incomplete` and defect are separate channels, word roles include `command_name` and `redirect_target`, comments are lexer tokens recorded on a tree side list, command-substitution interiors are sub-parses in a side table sealed below a top-level watermark, and keyword tokens are flagged ([#105](https://github.com/nanov/lesh/issues/105)). Syntax-layer work may refactor freely behind this contract and never break it — that is what makes the shell-core and leshper tracks parallel.

The highlight parse passes `aliases = nullptr` (the default), so spans point at typed text. Re-parse per keystroke is settled by measurement (38.7 µs at 4 KiB against N-1's 1 ms); incremental parsing is dead as a topic.

## 4. One event loop owns the terminal

[#98](https://github.com/nanov/lesh/issues/98), owner's principle: **all tty interaction goes through the event loop** — `tcsetpgrp`, mode changes, winsize, indicator writes. A tty syscall anywhere else is a defect. Signals become events on the same path. leshper consumes events and emits a render buffer (A-3/A-9).

The loop's *implementation* (libuv vs hand-rolled poll/kqueue) was held open for a benchmark, and **the benchmark has run** ([#115](https://github.com/nanov/lesh/issues/115), release build, p50 only, one process measuring all backends together): wake-to-callback **1.8–2.4 µs on every backend — indistinguishable**, the spread between two runs of one backend exceeding the spread between backends; idle turns on the bare Darwin `kevent()` floor (~13 µs) for both; timer lateness identical to 0.1% between hand-rolled poll-timeout and libuv (the once-observed 2:1 gap was `EVFILT_TIMER`'s doubled XNU slack, avoidable by not using it); **fork-quiesce cost is worker task granularity and nothing else** — byte-identical across backends, so #91's lever is how finely workers check in. What separates them was never latency: libuv costs **+57 KiB stripped** under ADR-0005 and, after one `uv_queue_work`/`uv_fs_*`/`uv_getaddrinfo`, spawns **four threadpool threads that survive `uv_loop_close` with no API to park or join** — quiesce-at-accept under libuv is a permanent never-touch-that-surface discipline, not a call.

**Decided ([#128](https://github.com/nanov/lesh/issues/128)): hand-rolled, `poll(2)` as the one backend, self-pipe for signals.** At ~4 fds `poll` and `kevent` sit on the same syscall floor and `poll` is POSIX — one file, no backend seam, kqueue/epoll never. Timers are the poll timeout (`min(deadlines) − now`, monotonic; never `EVFILT_TIMER`), and the mechanism is public: a **timer topic** lets an action arm a periodic timer through an additive ABI call (`lesh_timer_start(interval, action)`) — spinners and plugin ticks, §8's hook table arriving early; unarmed, it costs nothing. The loop's inputs are **topics** — `tty`, `signal`, `worker` (#126's wakeup fd, level-triggered and lossy: consume before draining the queue, check `POLLHUP` with `POLLIN`), `timer` — with the fd as each one's implementation detail, so §8's `fd-readable` hook is one more topic. A turn: `poll` → drain topics into events → `editor.step` each → if changed, `layout` → `blit.update` → write through the loop (#98). The core is a function over fds passed in — tests drive it with pipes and pty pairs, and the N-3 replay file goes through the identical path.

**Fork discipline — two layers, and the record on fish corrected**: only the loop thread forks, and it forks only when the workers are parked — `loop.quiesce()` (park workers, restore the terminal, `tcsetpgrp` handoff) before execution, `loop.resume()` after reap, and a debug assertion at every fork site. The owner asked whether "fork only on the main thread" suffices alone: it does not — `fork()` copies the calling thread but every other thread's *held locks* (malloc's, stdio's, the arena's) are frozen into the child, which deadlocks on first use. **fish does NOT park** — this session first recorded it as "like fish", and a read of the sources says otherwise: 3.7.1's `iothread_drain_all()` before `execute_fork()` sat behind `JOIN_THREADS_BEFORE_FORK`, default 0, "only used in the test suite"; fish 4.0.2 deleted the branch and demoted the drain to `#[cfg(test)]`. fish's actual contract is the *other* cure: between `fork()` and `execve()` the child touches only raw libc, stack buffers and pre-narrowed C strings (`FLOG_SAFE!`, `_exit`, "Called in a forked child! Do not allocate memory"), the signal handler re-raises in the child by `getpid() != MAIN_PID`, and one `pthread_atfork` child hook sets a flag for `debug_assert!`s — enforced by comment and caller discipline, not by the type system. **That suffices for fish because fish has no subshells**: every fork execs. lesh forks to *run shell code* — `( … )`, `&` on shell code, non-external pipeline stages — which allocates at once, so child-touches-nothing cannot be the whole answer here. Hence two layers: **parking makes shell-code-in-the-child legal** (ours, the load-bearing one), and **fish's async-signal-safe discipline applies on every exec lane anyway** — enforced, not commented: post-fork code in one file, a debug guard asserting zero allocations from fork to exec, `LOG_SAFE` the only logging reachable there, lane-aware assertions (`assert_quiesced()` at fork-and-continue sites, `assert_no_alloc_in_child()` on fork-and-exec paths).

**The door that removes parking (owner: v1 keeps parking, solve afterwards):** if lesh never forks to *continue running shell code*, every child is an exec-lane child and quiesce is deleted. The mechanism is **spawn-self** — `( … )` as `posix_spawn` of `lesh --subshell` with the parent's state over a pipe — and the POSIX contract it must preserve is exact (XCU 2.12): a subshell is a *duplicate* of the current shell, seeing unexported variables, functions, aliases, options, cwd, fds and the parent's `$$`, with nothing writing back — not a new shell. Cost hypothesis 1–2 ms vs ~100 µs for fork, plus a serialization surface equal to `shell_state`'s members. Prototyped and measured by [#132](https://github.com/nanov/lesh/issues/132); the decision returns to the map. Fish's C++-era pitfalls (fifteen, cited) are the loop ticket's traps section; the ones that shaped design: per-signal `SA_RESTART` policy (SIGINT without, SIGCHLD with), child-detection by `getpid()` never an atfork flag, per-errno `tcsetpgrp` policy, never re-enable ECHO around an action's shell code (fish #7770), reclaim pgrp and modes on every read entry (#9181), read the SIGWINCH counter before the ioctl, restore at exit only if the tty is still ours with SIGTTOU ignored first.

- **Terminal ownership**: the terminal follows the foreground command — `tcsetpgrp` to the child's group before waiting, reclaimed at reap (`WUNTRACED`). Job-control *plumbing* is in; `fg`/`bg`/`jobs` UI stays out (slots in later — [#98](https://github.com/nanov/lesh/issues/98) Q4's seam).
- **Ctrl-C while typing** is the rebindable `cancel-line` action ( `$?` = 130) **and the user's INT trap fires — the zsh way** (owner's call). During a command the kernel delivers to the foreground group; the shell only reaps.
- **Stopped children** without job control: reclaim terminal, report, `$?` = 128+SIGTSTP, prompt returns, process stays stopped.
- **No path leaves the terminal raw**: one registered async-signal-safe restore function on every exit path, fish/zle style; winsize re-queried at every read start.

### 4.1 Two owner threads (ADR-0009, [#136](https://github.com/nanov/lesh/issues/136))

**The shell is the main thread and owns `shell_state`; leshper's loop is a spawned thread and owns editor state and the tty while editing.** Owner's observation: leshper never mutates shell state, reads only parts of it, and only while nothing executes — so shell state needs exactly one owner and no concurrency mechanism. While editing, the shell thread serves three **latest-wins slots** in priority order — `execute`, `port_call` (an action's shell code, #92), `highlight` — waiting on a condition variable; a newer highlight overwrites a pending one (the cancellation). The loop reaches it by filling a slot; it reaches the loop through one wakeup pipe, a fifth topic in the loop's `poll`. **On the shell thread everything is serialized**: a writing port call, a read-only highlight and an execution never overlap, so `command_kind` is a direct lookup and aliases are classified from the real table (one level of resolution for kind; never expanded — spans stay on typed text). The only version left is the editor's generation on every shell→loop message. State-free reactors — history search, the autosuggester, path checks — stay on the stateless helper pool. Cost: ~5 µs per port-call round trip (#115), and a `$PATH` stat storm delays the next highlight, never dispatch — the highlighter polls `superseded` before every lookup. The fork is the main thread's; quiesce = helpers parked + loop waiting; the child claims the tty itself. Non-interactive lesh is unchanged: all of this is what an interactive read adds.

**Amended 2026-08-27 ([#168](https://github.com/nanov/lesh/issues/168) Phase A) — the loop is the HOST's, and it is not leshper.** Everything §4 and §4.1 decide about the loop still holds; what changed is *whose* it is. `loop.{h,cpp}`, `tty.{h,cpp}`, `workers.{h,cpp}` and `shell_actor.{h,cpp}` moved from `src/leshper/` to `src/ui/` and from `lesh::leshper` to `lesh::ui`. leshper is now **`step(state, event, now) -> effects` and nothing else**: no thread, fd, poll, timer, mailbox, or knowledge of shell, syntax, history or git. `src/ui/` is the **host** — it owns the poll loop, the terminal, the timers, the workers and the shell handoff, and drives the editor by sending events and performing effects, by no other route. "leshper's loop is a spawned thread" above should be read as "the host's loop is a spawned thread"; that it is a thread at all is the host's private choice ([#145](https://github.com/nanov/lesh/issues/145)'s fibers change nothing on the editor's side).

**The vocabulary, as it stands after Phase A.** Events in (`event.h`): `key_event`, `resize_event`, `worker_result`, `job_notice`, `injected_input`, `signal_event`, `paste_event`, `timer_fired{id, action}`. Effects out (`effect.h`): `render_request`, `worker_request{generation}`, `spawn_request` (still no producer — lane 2's future hook), `line_accepted`, `line_cancelled`, `end_of_file{status}`, `recursive_edit_request`, `arm_timer{id, interval_ms, action}`, `disarm_timer{id}`. Every one of them is trivially copyable and allocates nothing, asserted in the headers; the two exceptions are `injected_input` and `paste_event`, which carry text the user produced, and `spawn_request`, which is dead. A timer's `action` is an **interned handle** into the registry, not a name: the expiry path repeats once a second for the life of a `{time}` prompt.

## 5. Threads, forks, and the three lanes

[#90](https://github.com/nanov/lesh/issues/90)/[#91](https://github.com/nanov/lesh/issues/91)/[#92](https://github.com/nanov/lesh/issues/92):

- **Arena per worker, reset per request**; nothing points into a worker's arena after its request — stale results' backing memory is *gone* (N-4 structurally). Allocation counters go `thread_local`. **Latest-wins substitution slot per reactor**: one in-flight + one pending, overwritten on supersede; queue depth ≤ 1 by type.
- **Two fork regimes**: at accept every worker parks (a parked thread holds no mutex), then execution-time forks are free; while editing, the editor never forks — external execution is `posix_spawn`, exec-only (fish's answer since 2.0). No `pthread_atfork`; debug assertions that the pool is quiesced at every fork site.
- **The port** maps an action's shell code onto three lanes: builtins/functions in-process; externals (pipelines and `$(...)`-captures of externals included) via spawn; only fork-requiring forms (subshells, `&`, shell-code cmdsub bodies) refuse, loudly. fish's whole language is lanes 1+2; lesh keeps full POSIX at execution time. Recursion ceiling 64. Action writes to `$BUFFER`/cursor/selection apply **atomically on return** — one undo entry, one generation bump (A-12 intact). `exit` in an action is honored. [#11](https://github.com/nanov/lesh/issues/11)'s no-runner-for-completion guarantee stands.
- **Future door**: a dedicated executor thread would change the port's implementation (message passing), not its contract.

## 6. The registries are the seam

[#89](https://github.com/nanov/lesh/issues/89): no second shell language, ever — "other languages" are extension languages over ADR-0006's flat C capability surface, and **the ABI is bidirectional**: extensions register callables outward; registered code calls back inward (execute, variables, functions, actions). Four registries: **builtins** (one table, asserted both ways), **variables** (shell state), **functions** (moved to shell state, [#106](https://github.com/nanov/lesh/issues/106) — reachable for `lesh.myFunc(...)`), **actions** ([#93](https://github.com/nanov/lesh/issues/93), designed language-neutral per NG-4). No restructuring of `src/runtime/` until #93 forces it.

### 6.1 The action/reactor ABI ([#93](https://github.com/nanov/lesh/issues/93), ADR-0008)

**The registry stores the C shape; built-ins are its first clients — no native side door.** An action is `int32_t fn(lesh_editor*, const lesh_invocation*, void* userdata)`; the invocation carries invoking action name, key sequence, optional numeric argument. State access is copy-in/copy-out accessors over the opaque handle — no lent pointers, ever (the WASM insurance) — writes stage and commit atomically on return per #92. Loop outcomes (`accept_line`, `cancel_line`, `exit`, `recursive_edit`) are capability calls, never return values; positions are byte offsets that clamp and snap to cluster boundaries at commit, so bindings stay ignorant of grapheme geometry.

**Amended 2026-08-27 ([#168](https://github.com/nanov/lesh/issues/168) Phase A).** The four loop outcomes are still capability calls on the handle — `abi.h` is unchanged — but what the ABI records now *leaves* as an effect rather than being pulled back out of the editor: `lesh_accept_line` / `lesh_cancel_line` / `lesh_exit` / `lesh_recursive_edit` produce `line_accepted` / `line_cancelled` / `end_of_file{status}` / `recursive_edit_request` on `action_result::produced`, which `step` returns and the host carries out. The `loop_harness` latch and its `take_outcome` are gone. The same move took the timer table off the registry: `lesh_timer_start` / `lesh_timer_stop` keep their signatures and emit `arm_timer` / `disarm_timer`, the host owns `{id, interval, action, due}` whole, and an expiry arrives back as a `timer_fired` event that `step` dispatches — so a timer and a keystroke reach the action registry by one path instead of two. What the shell knows (§6.7) hangs off the registry as a borrowed `knowledge` pointer beside `completion` and `prompt_engine`, rather than being pushed through the harness.

**Reactors emit only through a generation-bound request token** — there is no apply path in the ABI, so applying a stale result is unexpressible rather than checked (N-4, the capability answer to "type-level" in C). v1 event kinds: `buffer_changed`, `cursor_moved`, `selection_changed`; the snapshot is buffer + cursor + selection + generation, nothing else. Emit calls copy at the call site; the emitting reactor is the decoration namespace; spans carry interned semantic style ids mapped by the theme at render (F-21). Cancellation is a cooperative superseded poll.

One `int32_t` status space (0 ok, negatives ABI, positives domain). Action names are `snake_case` with dot-prefixed unshadowable originals (`.accept_line`); registration replaces, so rc re-sourcing is idempotent (#101). Actions, registration and lookup on the loop thread only; handles valid only for the receiving call, debug-asserted. Growth is additive-only: the recorded doors are syntax queries on the token and provider access (#94). The Lua sketch that proves NG-4 — two trampolines, zero new entry points — is on the ticket. The header lands with [#107](https://github.com/nanov/lesh/issues/107).

### 6.2 The provider interfaces ([#94](https://github.com/nanov/lesh/issues/94))

**Four providers; one discipline; the syntax layer is sealed.** The A-5 set is the syntax layer (lex + parse — A-5's illustrative `Parser`, renamed because C-6 needs the lexer independently callable), `Completer`, `HistoryStore`, `Prompt`. The last three are override points (A-13); the syntax layer is not — a replaceable parser would repeal C-5. Jobs and variables are *not* providers: job notifications are loop events (#98), variable access goes through #92's port.

**Provider calls ride the request-token machinery** — one async discipline, two triggers: reactors receive tokens on events, providers on demand. Streaming is a token that emits N batches, each a pooled generation-tagged message applied by the loop (F-31 for free). The recorded exception: the syntax layer is synchronous on the loop thread (38.7 µs vs N-1's 1 ms; the Enter-accept decision cannot wait) — "for now, revisit if measurement ever disagrees" (owner). C-2's tristate is a **derived view** over the existing orthogonal channels — `incomplete()` wins while more input can come, else top-level defect → invalid — no third channel invented.

**The failure contract: native providers are trusted threads; user providers are killable processes.** User-supplied provider code (lesh functions) runs in a `posix_spawn`ed child in provider mode — shell state is loop-owned (#90) and editing-time forks are forbidden (#91), so in-process user code on a worker was never on the table. Slow → loses the generation race; hang → killed on supersede or deadline; crash → SIGCHLD; garbage → dropped at parse. F-18 becomes structural for providers.

**Contracts, minimally:** `Completer` = snapshot + cursor in, streamed candidates out — `(text, description, trailing slash-vs-space, needs-quoting)`, nothing richer until the engine asks additively. `HistoryStore` = dumb lesh-side storage (append, snapshot-iterate newest-first, entries preserve newlines per F-34); the *searcher* — F-32's line/prefix/token modes, F-33 — lives in leshper over C-6's lexer; v1 store is an append-only log file, the atuin-direction arrives later behind the same interface (owner's noted trajectory). `Prompt` = provider returns bytes for the four F-40 surfaces plus the transient variant; **leshper measures width itself** (one measurer: #108 tables + SGR skipping — no `%{ %}` folklore); PS1 expansion and any caching/pre-compilation are lesh-side, behind the interface.

**The hot-path rule, written:** sealed interfaces bind statically; override points may cost one indirection, and only at human-action frequency (Tab, recall, prompt draw). The keystroke path's sole indirect call is action dispatch — the price of F-13.

**vared is an ordinary client**: leshper's entry is `read(providers)`; command-line editing passes the default bundle, F-17 passes a different one (null completer/history, trivially-complete syntax). Recorded as the acceptance test [#102](https://github.com/nanov/lesh/issues/102) runs against these interfaces.

### 6.3 The selection model ([#96](https://github.com/nanov/lesh/issues/96))

**One pair, three paradigms: anchor + active flag, and the cursor is the head.** The region is derived — `active ? [min(anchor,cursor), max(anchor,cursor)) : none` — exclusive half-open, endpoints always on grapheme-cluster boundaries (debug-asserted; #93's clamp-and-snap already enforces it at the ABI). Emacs projects mark/point onto it; vi visual projects inclusiveness (+1 grapheme) in its mode's operators and rendering; helix uses it raw — a helix-mode motion writes `anchor := old head`, making noun-then-verb a keymap behavior, not a core variant. **Shape lives in the mode**: linewise and blockwise are act/render-time projections (zle stores linewise as `REGION_ACTIVE=2`; the lesh binding can synthesize that from the mode for compatibility). Blockwise is out of v1 and arrives as a projection, non-breaking.

Under every edit, the anchor follows the marker rules in `apply_edit` — before → shift, after → unchanged, inside → clamp to edit start — `active` survives, and undo records carry anchor + active. Multi-cursor is future-proofed by access discipline, not a vector of one: scalar primary, all access through state methods, ABI accessors singular now and plural additively later. Select-then-act sequencing (F-10) is recorded as a keymap-machinery constraint: operator-pending is a keymap-stack push. Owner's scope note: v1 shape, reworked in v2 if needed.

### 6.4 Keymaps as data ([#117](https://github.com/nanov/lesh/issues/117))

**Flat tables keyed by symbolic key events; the mode is the base of the stack.** A keymap maps sequences of decoder-output key events to action names — never raw bytes (zle's model reversed deliberately: the decoder owns escape sequences once, bindings stop being terminal folklore). `key_event` grows an `alt` bit (plus shift for named keys); **ctrl stays a C0 codepoint** — `<C-w>` is notation that parses to U+0017, because that is all the wire carries at the #97 floor. User-facing notation is **vim's** (`<C-w>`, `<A-Left>`, `<Up>`, literal printables).

**Dispatch**: top-down through the stack, first exact match wins; any prefix match anywhere holds the pending sequence until F-5's timeout resolves to the longest exact match. Two hatches: an **opaque** keymap stops lookup (the pager's map routes unbound printables to its filter action, F-29), and a keymap may name a **default action** for unmatched keys; the global floor is `self_insert` for printables. **Full mode switches swap the base** (`set_mode`; vi's `i`/Escape); **sub-modes are pushes** — visual (sets #96's `active` on push, clears on pop), operator-pending (a `pending_operator` state slot set by the verb, consumed after the next motion — zle's `viopp` written down), pager, history search. F-40's indicator reads the topmost keymap declaring an indicator string. Helix mode needs neither slot nor push — its verbs read the always-present selection.

**No remap problem exists**: bindings name actions, never key sequences, so vim's map-vs-noremap distinction has nothing to distinguish. The rc surface is the **`bind` builtin** (`bind -N`, `bind -m <keymap> <keys> <action>`, `bind -l`), mutating the keymap registry per #101's no-config-store rule; the neovim-shaped `lesh.keymap.set(mode, lhs, action)` arrives with the Lua binding as the second frontend to the same registry (#93's model). The registry lives in leshper beside the action registry, loop-thread mutation, ABI functions additive.

### 6.5 Vi depth at v1 ([#99](https://github.com/nanov/lesh/issues/99))

**zle's repertoire + counts + text objects; one keyed kill store; minimal `.`.** Motions `h l j k 0 ^ $ w W b B e E f F t T ; ,`, operators `d c y` with doubled-line forms, `x s r ~ D C Y p P`, mode entries `i I a A o O v`, counts multiplying the vi way (`d2w`, `3dd`). **Text objects are in** — their cost collapsed once #96/#117 made an object *one action in operator-pending mode that sets the selection to a range*: `iw aw iW aW` via the segmenter and C-6, bracket/quote pairs via one matching helper (the same helper helix's `mi(` wants later, built in neither paradigm's idiom). **One kill store**: emacs's kill ring and vi's unnamed register are the same keyed store, unnamed key as default; named registers arrive later as an addressable view, and the owner's noted trajectory is a clipboard-backed key (vim's `"+` shape, OSC 52 as the floor-compatible transport). **`.` ships minimal**: dispatch records the last change's (action, count) and replays non-inserting changes; repeating an insert-carrying change is the documented v2 step. **The boundary is a paragraph, not a surprise**: not included — named registers, marks, macros, visual-block, insert-repeat. F-11 is not bent: vi's only core ask was the `pending_operator` slot #117 already gave everyone.

### 6.7 What the shell knows, on the request token ([#130](https://github.com/nanov/lesh/issues/130); the version mechanism superseded by §4.1)

**Superseded in part by ADR-0009:** the verb, its resolution order, the memoized `$PATH` walk, the consumer rule and the `shell_knowledge` link boundary stand; the **copy-on-write definitions version is deleted** — with the highlighter running on the shell thread, which is the state's one owner, the read is local and no version is needed. The paragraph below is kept as the record of the alternative and why it was right under the previous thread model.

**One verb, and the version is a pointer the token holds.** `lesh_request_command_kind(request, name, len, out)` → `builtin | function | alias | external | unknown` — the highlighter paints F-21's classes, the autosuggester tests `!= unknown`; kind is free because it is the same lookup that answers existence. `$PATH` resolution runs on the worker (stat per directory, memoized per request — filesystem stays off the keystroke path, F-22). Enumeration verbs wait for the completer; a `path_exists` for F-27 waits for a consumer. Rule for growing this door: **a consumer, not a hunch.**

**How a worker reads state the loop thread mutates — fish's answer, applied to all three tables.** The definitions a worker needs — `$PATH`'s value, function names, alias names (the builtin table is static) — live in an **immutable, refcounted definitions version**. Mutation on the loop thread is copy-on-write: it produces a new version and swaps the pointer, copying only if a worker currently holds the old one (fish's `env_stack` `acquire_node_for_modification`; fish's `vars.snapshot()` in the `operation_context` is the same pointer grab). At submit the token takes the current pointer — **that is the claim** (owner: "the pointer and holding"); no copy at submit, no copy at claim, lock-free reads that are race-free by construction. Staleness is not the door's problem: a mutation bumps the generation, the in-flight request reads `lesh_request_superseded` and skips — the owner's "cancellation token" is the one that already exists. No parking is needed around #92's port for this; an action's mutation simply mints a new version while the worker finishes on the old. **Not chosen:** a concurrent dictionary per table — it makes each lookup safe but not the *set* of lookups, so one frame's spans could disagree with each other; only a version gives a computation one consistent view. **Link boundary:** `lesh_leshper` does not link the runtime, so the token holds a `const shell_knowledge*` — an interface defined in leshper, implemented at the wiring site over `shell_state` (A-5, the `history_source` shape); tests fake it.

### 6.8 vared, and the nested read ([#102](https://github.com/nanov/lesh/issues/102))

**Ships in v1 as `vared [-p prompt] [-c] name` — and it is the port's mirror.** The port crosses editor→shell (an action runs shell code); vared crosses shell→editor (a command, at execution time, borrows an editing session on the variable's current value, pre-filled). One nested-read mechanism serves both this and F-16's editor-initiated `recursive_edit`.

The bundle proves A-5: null completer, empty history (`vector_history_source{}`), a trivially-complete syntax provider — so no spans, Enter always accepts, and a literal newline is an ordinary bound insertion into the 2D buffer. Keymaps and modes are the user's own. On accept the buffer is assigned to the variable — with the `readonly` refusal *before* editing starts (status 1); `cancel_line` leaves it untouched (130); EOF on empty leaves it untouched (1). No history append, nothing else escapes. If the implementation needs any special case inside leshper, the ticket has failed its own test.

**While the nested read is open, the shell thread serves read-only slots and refuses writes** (owner's safety argument): it waits for the loop's reply *in its slot loop*, answering `highlight` (read-only) and refusing `port_call` with `LESH_E_REFUSED` — so the only possible wait cycle required a write, and writes are refused; deadlock is impossible by construction, and future editor-initiated nested edits get highlighting for free. Shell state is still written only from the shell thread's own straight-line execution.

### 6.9 The completion engine, kept simple and stupid ([#137](https://github.com/nanov/lesh/issues/137))

**v1 completes three things, synchronously, on the loop thread; the proper engine is a recorded v2.** Tab classifies the token under the cursor (C-6): command position (the `command_name` role) → command names; leading `$` → variable names; everything else → paths. At Tab the loop reads the name tables **directly** through the shell's `shell_knowledge` adapter (builtins + functions + aliases + the split `$PATH`; #130's enumeration verb, arriving with its consumer as the rule required) — no request, no copy: under ADR-0009 the only writers are the `execute` and `port_call` slots, both of which the loop itself requests and awaits, so a read from action code cannot race a write (a debug tripwire asserts it, #151) — walks the directory itself, and fills the pager. **Owner-approved deviation from F-31**: streaming-from-a-worker is deferred to the index stage — a Tab on a huge cold directory briefly blocks, as fish's did for years; the #94 contract is unchanged, so moving to a helper later is an implementation change only. **v2, recorded:** a command index/registry done properly; per-thread cached copies of the command list (it changes rarely); per-command and option completion; user completers through A-13; `$VAR`-in-prefix expansion via a safe path.

**One pager, three clients**: tab completion, history search (F-32), and the autosuggestion candidate view — columns, a kind marker as the only v1 description (`ls -F` vocabulary), own opaque keymap (#117), filter-while-typing (F-29), F-30's common-prefix insertion without opening, rendering into its own internal surface (A-6, unexposed). **Insertion**: `~` expanded for the listing, kept in the buffer; `$VAR` not expanded in v1 (the completer stays expander-free — #11's guarantee); directories complete with `/` and stay open, files with a space; `needs-quoting` applied to the inserted part only; every insertion through the accepting action (A-12).

### 6.10 The prompt engine: leshper state, configured across the ABI ([#157](https://github.com/nanov/lesh/issues/157), [#156](https://github.com/nanov/lesh/issues/156))

**The prompt is leshper state, pluggable through the C ABI — `bind`'s shape, a different registry.** A lesh builtin configures leshper's prompt the way `bind` configures its keymaps: through a narrow console the runtime declares and leshper implements (`prompt_console` beside `binding_console`, installed on `shell_state`, #118/#134), never a `lesh_runtime`→`lesh_leshper` link. The C ABI verbs (`lesh_prompt_module_register`, `lesh_prompt_set_placements`) are the language-neutral form the Lua binding reuses unchanged (NG-4); the console is the in-tree C++ caller, and a `bind`-shaped builtin is the later configuration surface. **The native prompt is modules, not an escape dialect** — bash's `\w` and zsh's `%~` are the folklore starship and prmt's users left behind. `PS1`/`PS2` are a transitional stub — the default provider renders them as literal bytes, as it does today, and the native prompt supersedes them rather than the shell growing POSIX `PS1` expansion for a mechanism on its way out (owner: PS1 support is dropped eventually, so its expansion is deliberately never built). **That supersession has arrived (owner's ruling on #157): the native prompt is the out-of-the-box default and `PS1`/`PS2` are the opt-out.** The shipped table is deliberately the quiet one — the working directory with `$HOME` contracted to `~`, then `"> "`, no colour and no segments, because a default is the prompt of everyone who has not decided yet and must not decide for them; the starship-shaped segments are one `prompt` away, and the group machinery is proved on the groups themselves rather than by shipping them. A `$PS1` still holding the POSIX `$ ` that `shell_state`'s constructor seeded is not a preference, so the stub renders only for a user who set the variable to something else — and for both surfaces together, never one each, because half-native is two prompts arguing. The first prompt-configuration verb takes the surface back for the rest of the session, as it always did.

**The element is the placement (owner's ruling on #157).** The template's five parts — module, style, type, prefix, postfix — are ONE record, `{core, params, pen, prefix, postfix}`, rendered as one two-phase span: the module is asked first, and the pen and the affixes are written only if it answered `ready`. A **module** still reads a shell fact and writes its bytes; a placement with no module *is* a literal, reports `neutral`, and therefore never votes; and **`(…)` is the only combinator**, holding placements and nested groups. This replaces the earlier model in which a styled placement desugared into a group and then had to be stamped with a module kind to keep voting in its parent — the bug that made `( on {git:magenta})` render nothing for ever while `( on {git})` worked, and which a record with a `style` field cannot express, because there is no node left to mis-stamp. **Modules are typed singleton objects owning their own type-slot grammar**: `parse` turns the type slot into an opaque `params_blob` once at SET time, refusing a bad one with the byte to look at (`path: unknown variant 'medum'`), and `render` is a pure function of the facts and those params — so `{env::USER}@{env::HOST}` is two placements computed once each by a per-prompt `(module, params)` memo that is a pointer plus a memcmp. Shell facts reach modules through the §6.2 provider seam (`shell_knowledge`), on the shell thread under ADR-0009 — `path` from `$PWD`, `status` from `$?`, `jobs` from the job table — never by reaching across the link boundary.

**A group shows iff a child inside it is ready; decorations do not vote.** Element status is `omitted | ready | pending | neutral`: a module returns the first three and a literal returns `neutral`, so `({literal:magenta:: on }{git:magenta})` renders ` on main` in a repo and nothing at all outside one, the literal and the style vanishing with the module (starship's `(…)`; prmt's prefix/postfix are slots on the placement itself and need no group). **The vote recurses through what each child reports** — a nested group answers `ready`/`omitted` exactly as a placement does, so `(({git}))` behaves like `({git})` and redundant parentheses change nothing; the earlier model counted only direct module children, which made a nested group a permanent blank. Evaluation is two-phase — the children that have something to compute first, into scratch, and the decorations only if the group survives — so `git` is never even asked for its bytes when it is `omitted`, and a literal inside a vanished group costs neither bytes nor a call. This is what makes user-written skippable literals expressible where a flat sequence could not: binding is explicit grouping, never inferred from adjacency.

**Recalculation is per element, by cause — the prompt is never recomputed wholesale.** Each element owns an output slot (its last bytes) in the prompt arena; a render re-invokes only the elements with a reason and splices every other slot unchanged, then lays out, diffs (#112), and blits — so a tick that animates a spinner re-invokes the spinner alone and `git`'s slot is memcpy'd. The three reasons, and an element answers only its own: **a new prompt** (the boundary — the only time `git` runs); **its own wake tick**; **an event it declared interest in** (its `pending` completion, its FS watch, the vi-mode change for the mode indicator). Unchanged output produces no terminal write, because the diff finds no changed cells.

**Ticking is one virtual clock on the loop's timer topic.** Time is counted in **ticks of 10 ms** (`tick = monotonic_ms / 10`, integer); an element asks `wake_in(n)` and the composer keeps one deadline list, arming the loop's single prompt timer for the earliest — nothing runs every 10 ms, and an empty list is no timer at all, so a static prompt causes zero idle wakeups. A tick re-invokes the same render function (no separate callback); **animation state is derived from the tick**, not stored (`frame = tick / cadence % n`), so two spinners share the clock and spin in phase, a parked stretch causes no catch-up burst (rearm-from-fire), and #109's replay reproduces the exact frame sequence — the tick is the state. Genuine per-element state is an arena-owned blob the module's `parse_arg` allocates, never a static. Ticks pause during execution (the prompt is not visible, the loop is parked), and everything due in one fire coalesces into one `needs_render` and one diffed blit. Where ZLE offers `TMOUT`/`TRAPALRM` at one-second resolution with a full `reset-prompt`, this is millisecond-grid and cell-diffed.

**Performance, and the two rules that make its floor unconditional.** The per-prompt path is a loop over a handful of function pointers into a rewound arena plus the module work, which is syscalls, not framework — a typical `path + git + status` prompt renders well under 100 µs in-process, against prmt's ~2 ms and starship's 10–50 ms, both of which pay a process spawn per prompt. The floor is guaranteed because **the synchronous set is memory-only** — anything touching the filesystem (`git` reading `.git/HEAD` is filesystem work) is a **budgeted** module that blocks only up to a small tick budget and is patch-in capable, so prompt-appearance time never depends on an NFS or `/mnt/c` mount — and **built-in modules never `exec`** (starship's slowness is `node --version`-class spawns; detection is a `stat`, versions are small file reads). A user module that must exec is a killable child under the budget (A-13/F-18).

**v1 is the §6.9 size; the async half is v2.** v1 ships the registry, the composer, the tick wheel, a `constexpr` default prompt, and configuration through the ABI — and, since the owner's ruling on #157, the `prompt` builtin and the `{module:style:type:prefix:postfix}`+`(…)` template language that were its recorded follow-up. **The language is prmt's, adapted**: prmt's empty-slot defaults kept verbatim (`{git:magenta::on :}`, `{env::USER}`, a trailing colon legal, a sixth field refused), nestable `(…)` groups, `{literal:style::text}` for a styled standalone literal — a placement with no module, so it never votes — the `\:`-family escapes, and the string grammar below as its style slot. It is **parsed once at set time into placements and never at render**: where prmt re-parses per draw and must therefore degrade a malformed placement into literal text, this refuses with one sentence naming the offending byte and leaves the prompt that was standing standing. And it is **one grammar at two evaluation times** — the same walk drives a `constexpr` validator, a `consteval` builder and the set-time builder, all three calling the modules' own `parse`. The shipped default is therefore its own spelling COMPILED — `kDefaultLeft = compile<"{path}> ">()` — so there is no second statement of it to drift, and a default that stopped parsing is a build failure rather than somebody's blank prompt. There is no intermediate AST and no second composer. Modules: the memory-only set (`path`, `status`, `jobs`, vi-`mode`, `time`, `duration`, `env`) plus a **budgeted `git` branch** — a hand-rolled `HEAD` reader (symbolic and detached HEAD, loose and packed refs, gitfile indirection) with "unrecognized layout → spawn `git`" as the correctness fallback. Surfaces: left and continuation. **Deferred to v2, all recorded on #156**: `git status --porcelain=v2` as a killable child under patch-in (and therefore the `pending` spinner and the completion-event path — v1's loop-integration surface is timers only, never completion events); the FS-watch branch cache (a directory watch as a loop wake source that moves `git` into the memory-only set after first read, with the register/deregister-on-cwd lifecycle); the right prompt, the transient prompt, and the mode indicator's context tweak; libgit2 as a per-module choice only if `git status` correctness ever demands it; and the two combinators the redesign deleted — a `when` that gates its children on a predicate of the facts and an `either` that falls back from one placement to another. Both were C++-authored vocabulary no template could spell, and **nothing a template cannot spell may remain in the engine**, so they were removed rather than kept for a consumer that never appeared (prmt has neither); they return as GRAMMAR the day a consumer asks for one. Styles in v1 are a `style`/`color` value emitted to SGR through #131's pen (quantization stays the blitter's, #97) — no string parser: the default prompt is a `constexpr` table, so a style is `style<"cyan">` or a raw value, and nothing hands the engine a style *string* to parse. The **string grammar** (prmt's `cyan.bold` / `#hex+bg`) arrived with its first string source — the template language's style slot and `lesh_prompt_set_placements`'s `style` option — and sits beside `sgr.h` as `style_grammar.h`, to be **shared with the highlighter's theme** (#141) so one parser serves both. Deferring it is deferring a parser, never the SGR emission, which v1 has.

### 6.6 Logging, and the replay harness as its client ([#109](https://github.com/nanov/lesh/issues/109))

**One recorder, two sinks; level × category; off by default; trace compiles out of release.** Every message carries a level (`error warn info debug trace` — neovim's axis) and a category (`loop dispatch reactor provider spawn worker render history exec parse event` — fish's `FLOG` axis); enabled by `LESH_LOG=<level>[:<cat>,<cat>]`. **Cost rule**: a disabled log is one relaxed atomic load and a predictable branch, arguments evaluate only past the check, formatting uses a fixed thread-local buffer (truncate, never allocate), and `trace` is `#if`'d out of release — N-1 never sees logging. **Destination**: `$LESH_LOG_FILE`, default `${XDG_STATE_HOME:-~/.local/state}/lesh/log`; **never stderr while leshper owns the terminal** (#98); stderr only for a non-interactive shell with an explicit level; a startup `info` line records version, pid, tty and the floor-detection result.

**The N-3 replay harness is a client**: the `event` category logs every loop input — key events, resize, signals-as-events, worker-result arrival with generation and timing — and a **structured sink** (jsonl, one object per line) writes it when `LESH_REPLAY_FILE` is set; replay feeds the file back through `editor.apply` and compares with the state struct's existing equality. A second event serialization is the bug this prevents. The owner's dashboard instinct (#94) is a third client of the same records — nothing built. **Redaction**: buffer contents and key codepoints appear only at `trace`; `debug` logs lengths and action names, so it is safe to attach to a bug report; the replay file necessarily contains full input and the docs say so. Lives in the substrate (`src/substrate/log.{h,cpp}`) — shell core and leshper both use it, and it depends on nothing above the substrate. Text format `HH:MM:SS.mmm LEVEL category thread: message`.
